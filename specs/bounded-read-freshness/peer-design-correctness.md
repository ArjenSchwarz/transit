# T-63 design peer — correctness and feasibility

Reviewed the complete requirements, revised design, critic report, explanation, decision log, and both isolated prototype sources. Also inspected the existing server's batch dispatch/body limit and the canonical task snapshot implementation directly from merged revision `201205bd4e786c7f152d8f99006b37da7da888c7`. This is one independent internal peer perspective in the documented two-peer fallback; no external-model calls, builds, production edits, or approval actions were performed.

## Verdict

No remaining design blocker in the revised document. The design can proceed to user review with its explicit implementation verification gates. The probes establish narrower facts than the complete production contract: they do not establish live CloudKit coherence, large-batch response availability, actual retained-store transactions, or a hard real-time scheduler guarantee.

## Critic findings independently assessed

- **Whole-batch fallback and physical accounting:** the original blocker was valid. A small array assembled after individual timeouts cannot establish a deadline for arbitrary candidate aggregation. Preparing the complete fallback before worker dispatch and selecting it through an independent batch gate removes the dependency on candidate serialization. Retaining one completed element's physical permit through aggregation prevents repeated timed-out assemblies escaping the eight-operation bound. The ownership transition must be atomic; the current prototype does not exercise that transition or a blocked large aggregate.
- **Publication transaction:** the original blocker was valid. Prepared success bytes can contain snapshot/cursor IDs, so response selection and publication must share one critical section and reject the entire selected set before any commit. The revised pre-encoded rejection/fallback rule prevents returning IDs that were never published. Validation, nonthrowing commit, and discard must be effect-free with respect to arbitrary work: no callbacks, nested store locks, encoding, or final destruction of large values inside the domain.
- **Complete portfolio evidence:** the original blocker was valid. Optional task evidence alone cannot distinguish an intentionally narrow read from an incomplete portfolio. The explicit completeness discriminator plus construction/consumer validation addresses this. Empty comments are valid complete evidence only after a successful required fetch; absent required evidence must never become an empty list.

## Additional concurrency finding and disposition

I independently identified the same-store batch hazard reported by the architecture peer: validating two independently prepared whole-index replacements against version V before committing either would let both pass, then the second swap could overwrite the first. A lock and validation-before-commit alone do not prevent this intra-batch lost update.

The latest design addresses it by coalescing selected create/append operations into one aggregate candidate, version, and capacity reservation per store outside the gate, then validating every aggregate before swapping each store index once. This is sufficient at design level. Implementation tests must cover multiple creates, multiple appends, and create-plus-append in one read-only batch. Transfer ownership from child pending reservations to the aggregate atomically so capacity is neither double-counted nor briefly freed; each discarded/unselected reservation is released exactly once. Concurrent operations changing the base version must select the documented pre-encoded rejection rather than partially publish the batch.

## Early verification priorities

1. **Saved capture/history fence:** equal valid persistent-history watermarks are a defensible optimistic fence only if all relevant saved changes contribute visible history and the validation context observes the latest watermark. Test concurrent imports, history purge/expiry, genuinely empty stores, and fresh contexts with pending UI changes. An empty selected result is not proof that the entire persisted domain store has no history. Unsupported fencing must fail with `incoherent_capture`, including inactive sync, rather than quietly weaken the saved observation boundary. The current local probe proves rejection of one intervening save, not the full assumption.
2. **Import applicability:** positive store-ID association and actual visibility of the completed import remain necessary. A callback's receipt time or an unchanged monitor generation does not by itself prove that the selected context includes that import. Define the monitor's serialized boundary and test queued callbacks; preserve `unknown`/null import time whenever association or visibility cannot be supported. Reject future/inconsistent event clocks rather than giving them zero age. This uncertainty concerns freshness separately from local capture completeness.
3. **Admission-to-router deadline:** measure fallback preparation, strict timer selection, continuation scheduling, and router return with the existing 1,048,576-byte body limit, long request IDs, many invalid/busy elements, and large candidate result arrays. Preparing fallback is inside the approved budget; starting a timer after expensive preparation cannot reset admission time. Reserve the absolute cutoff first and test preparation finishing close to it. The isolated six-second blocked-MainActor result supports timer independence but does not prove these cases.
4. **Permit/lifecycle races:** test timeout before worker starts, capture-to-assembly transfer, stop/restart, disconnect during preparation, and late physical completion. Every physical operation must retain exactly one permit until its actual final stage ends. Requirement 1.6's stop wording should be interpreted with the approved unfinished-work bound: stopping invalidates response/publication state but does not make unfinished physical work disappear.
5. **Publication visibility/capacity:** test stale append versions, expiry during preparation, capacity rejection, token collision, canceled batches, and lookups racing a commit. Capture capacity usage before, during, and after aggregate reservation transfer. Pre-encode all selectable error bytes before the gate; after rejection, no successful response may retain a staged ID and no lookup may expose an uncommitted entry.

## Merged foundation and alternatives

Merged `MCPRecordSnapshot.task` fetches comments through the task UUID descriptor and includes their full covered fields in canonical r1. Public comment omission or effective-status projection must preserve that revision verbatim. Portfolio relationship attribution can use physical keys without substituting a different comment set into the authoritative revision routine. The design correctly keeps ordinary summary reads without requested comments on their no-fetch path.

A typed complete-portfolio wrapper with mandatory revision/record/comment evidence would make invalid states harder to construct than an enum plus optional properties; this is a worthwhile implementation choice rather than a design blocker because both construction and consumption already require validation. If persistent-history fencing cannot be established, do not invent a substitute query-generation guarantee: use the documented failure and return an alternative capture mechanism to the design gate. A structured timeout race or MainActor timer is not a viable substitute for the independent completion mechanism because synchronous store work can prevent timely cancellation or actor execution.

User design approval remains separate. These findings do not authorize tasks or production implementation.
