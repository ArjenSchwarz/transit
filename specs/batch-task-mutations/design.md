# Design: Batch Task Mutations

Review status: approved by owner in parent at `Sentinel_717be95229c48191a7c41b6e5e467e4c` for commit `a5950e9`. Task plan and conditional implementation approved at `Sentinel_edf7fd12288c819192ad45a04154372a`; external delivery/ownership/test-slot conditions still apply.

## Architecture

Add `mutate_tasks` as a core domain tool. Its mode selects pure preview or ordered calls to the existing app-owned `MCPWriteCoordinator`. It has no persisted batch model, guard, key namespace or recovery engine. Latest-only transport validation remains T2383's responsibility; `tools/call` notifications never reach this tool. See requirements 1–5 and ADRs 4–5.

Place batch request, preview, orchestration and result code in `MCP/BatchWrites/`. The handler supplies the shared container plus its existing write services/context and optional app-owned write coordinator; constructing a coordinator or opening reservation storage while handling a preview is forbidden. ModelContext, models, dictionaries containing Any, and ValidatedTaskUpdate stay on MainActor. Only immutable JSON evidence/encoded bytes and value identities cross actor boundaries through the approved T2383 adapter.

### Input contract and validation

```json
{"mode":"execute","items":[{"itemId":"canonical","operation":"update_task","arguments":{"taskId":"00000000-0000-0000-0000-000000000001","name":"Canonical","expectedRevision":"r1:<64 lowercase hex>","idempotencyKey":"workflow.canonical"}}]}
```

`mode` is exactly `dry_run` or `execute`; `items` contains 1–50 elements. Each item has exactly itemId, operation and arguments. No outer batch key or required correlation ID is added. Input indexes are zero-based and itemId must be a non-empty string; whitespace-only IDs are rejected. Original IDs/argument strings are otherwise preserved.

Validate the complete shape before model fetch, key acceptance, or execution. Reuse `MCPWriteCommand.validate` for nested operation fields and safety formats, with the additional batch restrictions: taskId is required, displayId is forbidden, unsupported operation/fields are rejected, metadata values must be strings, and repeated itemId, normalized target UUID or (operation,key) pair is rejected. UUID equality is used only for collision detection/mapping; original argument spelling reaches canonical request binding unchanged. A batch-local schema mirrors the three protected argument schemas without changing those schemas.

Publish conditional nested schemas for the three operation branches, `additionalProperties:false`, required safety fields, array minItems/maxItems and key/revision patterns. String-valued domain enums (status/type/priority) are validated at the item domain stage: the batch schema describes allowed values but accepts strings with no enum/const restriction so an invalid domain string does not trigger an unintended whole-batch shape rejection. Wrong JSON types and required-field omissions are shape failures; missing conditional status-comment author is a domain failure. Diagnostics contain index, usable itemId, field and existing input error code. No keys are accepted for shape failure.

### Pure preview

MCPBatchTaskPreview creates a fresh MainActor ModelContext over the same persistent ModelContainer, sets autosaveEnabled false before access, and constructs read-only validator services in that context. Fetches explicitly exclude pending changes. It reads saved records only: unsaved UI inserts, edits and deletions in container.mainContext are neither copied, returned, saved, rolled back nor refreshed. No await, transaction, model assignment, insert/delete, rollback, save, receipt lookup, cleanup or coordinator call occurs in the preview pass. observation is saved_local_store; no globally fresh/import-complete view, cursor or snapshot is promised. If durable storage is unavailable, items are unavailable without returning temporary in-memory records as saved evidence.

The preview pass validates all items against locally saved observations; it is not a multi-fetch database transaction. New saved local changes or imports before execution can change results. Unsaved UI state is never used to certify a preview. The shared UI context is untouched, including its original autosave flag and pending changes; only the privately owned read-only context has autosave disabled.

Resolve each task with a batch-only UUID fetch that establishes exactly one match, rather than `TaskService.findByID`'s first match. Zero matches returns TASK_NOT_FOUND; multiple matches returns DUPLICATE_TASK_IDENTIFIER; fetch failure is unavailable. Capture `MCPRecordSnapshot.task` including complete comment-covered revision evidence; only then project away comment bodies in preview output. A required snapshot/comment failure makes that item unavailable, never a valid empty observation. Compare expectedRevision for update/status items; add_comment has no precondition.

| Operation | Read-only validation and proposed effect |
| --- | --- |
| update_task | Reuse TaskUpdateValidator.validate and its read-only milestone resolution. Convert ValidatedTaskUpdate to changed fields/clear actions while still on MainActor; never call apply. Name/description normalization and metadata/milestone precedence match existing command behavior. |
| update_task_status | Share pure status/author/comment-input validation with MCPWriteCommand. Compare task.status using the existing service's same-status logic; describe raw status change and timestamp effects symbolically. A blank comment with a valid required author produces no comment. No timestamps or new comment identities are generated. |
| add_comment | Share pure comment content/author trimming validation with CommentService. Describe normalized comment fields with isAgent true. Never construct a Comment or allocate its UUID. |

Extract only pure validation helpers required for parity, leaving mutation and saving in the existing services. `MCPTaskMutationValidation` in MCP/BatchWrites covers MCP-specific status/comment inputs. Cross-platform pure comment normalization belongs in Services/CommentInputValidation.swift; CommentService uses it while retaining its save/resolve/error behavior, so iOS never depends on a macOS-gated MCP file. Preview valid means current domain constraints were satisfied; `keyState:"unchecked"` and `advisory:true` always accompany it. Persistence fallback is reported as unavailable saved evidence; the preview does not certify sidecar/store ownership or future writes.

### Execution and transaction boundary

`MCPBatchTaskCoordinator` owns the ordered loop, not durable state. After complete shape validation, prepare the compact recovery fallback. Before every item, check observed cancellation. The coordinator handles dirty-context saved-replay versus new-write availability without a loop-level receipt-blind block. Invoke the existing coordinator once with the exact original operation arguments and a batch-only pre-apply identity validation policy. Capture its complete result immediately; verify/classify that evidence before any next item. No live preflight is allowed before receipt replay.

Extend the coordinator internal execute path with an optional batch execution policy, default nil for standalone calls. It contains a clean-context requirement at fresh phase boundaries and a MainActor synchronous throwing pre-apply identity callback. When the shared write context has pre-existing pending changes, permit only read-only retained-outcome inspection before deciding write availability; neither save nor roll back those edits. The outer loop does not suppress saved replay or key-reuse detection.

Inside the existing coordinator, extract the read-only portion of retained inspection using only reservations.withValidatedBindings/lookup and receipts.lookup(durable:true). It validates the original local scope, payload binding, receipt association and expiry using existing validation. A valid unexpired durable terminal receipt returns its original replay even while UI edits are pending; retained different arguments return existing IDEMPOTENCY_KEY_REUSED. This dirty-context path never calls reserve/recordExpiry/reconcile/cleanup/recover/recoveryHook/save/rollback or fetches the task. A missing sidecar binding does not require repair to replay an independently validated terminal receipt in the same store scope; an existing inconsistent association or unreadable binding is uncertainty, not permission to use a new key. Accepted/unresolved evidence requiring recovery cannot progress while dirty. This is a read-only branch of the same coordinator/store APIs, not a second receipt engine.

If no protected replay/key-conflict result can be established while dirty, return an existing uncertainty-shaped result with accepted null (or true where the prior accepted binding is established) and reconciliation direction; no new key/domain effect is accepted. Next items are unattempted. Missing/expired receipts do not establish that the original effect never occurred. For clean contexts, the existing repair/recovery/acceptance path remains authoritative.

The clean-context policy guards fresh mutation-capable phases before any baseline save/cleanup/recovery and guards accepted execution after every suspension before baseline/rejection/commit work. Dirty detection returns directly before entering a phase, never throws into an existing rollback/recovery handler that might discard UI edits. No actor suspension exists between a clean check and that synchronous phase. Own acceptance/domain/receipt changes created within the phase are allowed; do not mistake them for unrelated edits. Dirty detection after acceptance returns accepted true/uncertain without terminal save, rollback or recovery, retaining the accepted binding under existing T2380 semantics. Once the UI owner independently saves/discards pending edits, original-key retry uses existing durable recovery, which can conclude no-effect rejection rather than rerun an interrupted item.

Call the identity callback inside the existing commit scope immediately before command.apply, after fresh binding validation and a clean baseline. It receives original command/target and existing service context, fetches all UUID matches and requires exactly one. No suspension lies between this check, target re-resolution, revision validation and apply. Ordinary validation errors follow the existing rejection/recovery path; only dirty-context safety stops bypass terminal-saving work. Retained read-only replay and active-key outcomes preserve existing results and bypass live identity validation even when the target is missing or ambiguous. Original standalone calls retain default-nil policy and existing behavior; reservation/receipt store files, payload/format/expiry algorithms and storage schema are unchanged.

The advancement predicate for T2380 v1 source is explicit:

- contractVersion is JSON numeric integer value 1 (including equivalent numeric spelling such as 1.0, matching T2380 canonical validation, not Boolean/coerced string), outcome is the string committed, accepted is JSON Boolean true, tool/key exactly match the submitted operation/key, and original optional isError is absent or Boolean false.
- entityId and saved record identity are valid UUIDs. For update/status, entityId and record.taskId equal the input task UUID. For add_comment, entityId equals record.id and record.taskId equals the input task UUID. UUID comparison does not alter source strings.
- record is an object with revision matching r1:[0-9a-f]{64}. For a nonblank requested status comment, the accompanying comment object has its own valid UUID/revision and the same taskId; a blank/absent comment does not require a fabricated comment.
- completedAt/replayExpiresAt are parseable UTC ISO 8601 millisecond strings with expiry later than completion. This validates terminal evidence, not current retention: do not compare expiry with the classification time to downgrade established commitment.

Unknown fields remain preserved; unsupported versions, absent/null/wrong-type required evidence, unreadable/malformed evidence or contradictory identity/error fields stop progression without assigning a new receipt classification. These checks establish the supported source contract, not a new hash of the record or certification of current contents.

Rejected/in_progress/uncertain results stop normally. Unknown evidence stops with a batch diagnostic. A stop descriptor carries reason (item_result, evidence_unavailable, pending_edits or cancelled), nextUnstartedIndex and optional attempted blocker {index,itemId}. An unsuccessful/unreadable attempted result supplies its blocker; cancellation before item zero or between committed items has no attempted blocker; a dirty-context coordinator stop identifies its attempted item even though no new effect/key acceptance occurred. Remaining items are not_attempted, refer to the stop descriptor, and have no coordinator invocation attributable to this loop.

Check cancellation after each returned outcome as well as before the next call. If the current item returns an unsuccessful/unreadable outcome, that result determines stopped/evidence_unavailable summary and optional observedCancellation diagnostic, preserving its original evidence. If it commits and items remain, observed cancellation produces interrupted with the next unstarted index and no failed blocker. If every item committed, summary remains all_committed even when cancellation is observed afterward; transport can still suppress delivery. A caller timeout/lost response alone is not observed cancellation. No loop task is detached to continue after observed cancellation, and no cancellation undoes a durable receipt.

### Clean-phase policy coverage

| Existing coordinator path | Batch policy boundary |
| --- | --- |
| execute active-key handling; acceptSynchronously before existingOutcome/baseline/cleanup | Active result remains read-only. Dirty context uses non-mutating retained inspection only; valid replay/key mismatch returns normally, otherwise uncertainty. Clean entry uses existing path. |
| existingOutcome → recover; missing sidecar repair | While dirty, no recover/repair hook is invoked. Durable terminal evidence can replay without repair; accepted/missing/inconsistent evidence stops. Clean path retains existing repair. |
| runAccepted preparation success | After await, direct clean check before baseline/commit; dirty returns accepted-true uncertainty without catch/rollback/recovery. |
| runAccepted preparation exception/cancellation | After await/error, direct clean check before baseline/completeRejection; dirty preserves UI edits and accepted binding. |
| acceptance-save failure → rollback → rejectBeforeDomain | Entry was clean and phase synchronous; only own staged changes can be rolled back/rejected. No unrelated UI state can interleave. |
| commit failure → rollback → recovery → completeRejection | Entry was clean; synchronous own-mutation rollback/recovery remains existing behavior. |
| terminal-rejection failure → rollback → recovery | Entry was clean; only own receipt state changed. Never enter this path from a dirty pre-phase stop. |

No batch-level lock is held across awaits and different batches can interleave between items. Shared item keys use the existing active-key protections; different keys can conflict through revision checks. This is ordered per-item execution, not an isolation guarantee for the whole plan. Historical canonical replay can advance to new closures after later edits; clients requiring current canonical contents reconcile separately.

## Result contract and serialization

The following names define T2384's logical payload, not common MCP transport types or T2383's wrapper/API.

| Logical field | Contract |
| --- | --- |
| contractVersion, mode, atomicity | 1, dry_run/execute, per_item. |
| summary | preview_valid/preview_invalid for preview; all_committed/stopped/interrupted/evidence_unavailable for delivered execution. confirmedCommittedCount counts only established commitments; stop carries reason/nextUnstartedIndex and an optional attempted blocker. Shape errors use rejected_input with indexed diagnostics; encoder fallback uses serialization_failed. |
| items | Input-ordered mapped entries carrying index/itemId/operation/idempotencyKey/original taskId. |
| item originalResult | Complete original parsed JSON value when readable, original text string, and original optional isError, preserving absence/null/unknown fields. Source and supplemental batch diagnostics are separate members. |
| preview observation/effects | Current record/revision when obtainable, changed fields/actions or normalized proposed comment, valid/invalid/unavailable state, advisory true and keyState unchecked. No committed metadata. |
| not_attempted diagnostic | Reference to stop reason/next index and optional blocker. No newly accepted flag, receipt, saved record or expiry is fabricated; existing keys could independently have prior outcomes. |

Parsed original results are transported losslessly through the approved T2383 JSON representation, not reconstructed using a typed known-field encoder. Original optional isError is absent when absent, rather than converted to false/null. Aggregate isError is true for input failure, any unsuccessful/unverified/unattempted item, invalid/unavailable preview, interruption or encoding failure. It is absent for all committed or fully valid preview results. Source receipt fields and original error flag are never changed to match this aggregate flag.

Supply the generated batch logical JSON and its compatible text as one source to T2383's approved source/presentation adapter. Its proposed immutable-source, collision-free source/presentation separation is the coordination boundary; exact common production type names, function signatures, output-schema plumbing and modern envelope are owned by T2383's approved design. Supplemental categories/links never overwrite nested source fields or retryAction. No serializer implementation is duplicated in this feature. Batch output schemas accept arbitrary unknown JSON inside retained source evidence and distinguish unavailable parsed evidence from explicit null.

Before any execute call, prepare the complete deliverable serialization_failed fallback through the agreed T2383/T63 transport adapter, including tool text/structured presentation, request ID/correlation, required modern result/metadata fields and fully encoded HTTP body bytes. Its logical recovery payload contains input indexes, operation names, original keys and task UUIDs plus reconciliation guidance. Omit unbounded itemId/record/raw-text fields; index maps to the retained original request. The adapter returns ready-to-select immutable bytes, not a logical value requiring a second pass through the failed encoder. No JSON/source/presentation/envelope encoding occurs when selecting fallback. T63/T2383 retain response selection and cancellation ownership; writes acquire no read-retention publication.

If complete fallback preparation fails or the approved shared adapter cannot provide this contract, execute no item. On unreadable item evidence, preserve raw text/isError if the normal failed aggregate can encode; otherwise select the complete preencoded fallback. If final payload/adapter/envelope encoding fails after effects, select those already deliverable bytes without reinvoking any failed encoder. It does not claim all effects uncertain, rejected or unattempted: batch effect knowledge is unestablished and original-key recovery/reconciliation is required. HTTP stream cancellation suppresses delivery; the app-owned coordinator's committed receipts survive.

Retry guidance preserves nested receipt directions. Matching retained item requests can be regrouped into another batch or called through their original protected tool, with the same exact arguments. Retained conclusive rejection stops identical-batch continuation until the caller excludes it or corrects it with a fresh key; transient same-request-retry outcomes keep their existing direction. Never use a fresh key to escape uncertainty. After replay expiry, or response loss with no establishable retention window/originating store, reconcile rather than assume missing receipt means no effect.

## Risks and Assumptions

- Risk: saved-only context/fault handling or phase guards unexpectedly access or flush unrelated UI state | Verify: early owning-container fixtures with pending inserts/edits/deletes and independent durable readback, plus UI edits injected during accepted preparation, before shared wiring | If wrong: stop batch availability and retain existing receipts without effects until the no-save boundary is proven; never expose or flush pending UI state as a fallback.
- Risk: large historic records exhaust aggregate encoding resources after commits | Verify: early encoder fault-injection and production-shaped record tests before shared adapter integration | If wrong: select the preencoded reconciliation fallback and preserve receipts; do not add a success truncation/byte limit without requirements review.

## Research basis

Repository sources settle operation normalization, first-match UUID lookup, coordinator replay/commit placement, snapshot coverage and existing schema limitations. [Apple's SwiftData introduction](https://developer.apple.com/videos/play/wwdc2023/10187/) describes contexts tracking pending edits and fetch options including excluding unsaved changes; preview uses its own context and explicitly excludes unsaved changes. The saved-only expectation comes directly from owner at Sentinel_bb00a4d9d8688191a33a0e6a34ea38db. Apple API reference pages were located but their Markdown content could not be read through this tool; no undocumented autosave guarantee is assumed, and the saved-only/dirty-phase fixture gate above is mandatory. No callable Context7 tool was available; local installed code and primary Apple documentation were used. T2383's approved requirements and design coordination define the transport/result boundary; T63/T2382 approved designs remain read-only dependencies.
