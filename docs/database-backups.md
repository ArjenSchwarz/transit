# Database backups (T-2431)

Settings → Backups is available in normal Release and development builds on Mac, iPhone and iPad. Scheduled exports are Mac-only.

## Archive and import

A `.transitbackup` file is versioned JSON. Files are plaintext and unencrypted, including task content, comments and MCP request/receipt payloads. Keep the destination private, especially if it is synced or shared. Version 1 covers every stored scalar field of Project, TransitTask, Milestone, Comment, SyncHeartbeat, MCPWriteReceipt, TaskLinkOccurrence, TaskLinkRemovalEvidence and TaskConsolidationEvent. Raw enum strings, malformed metadata/history payloads, optional values, timestamps, UUIDs and display IDs are preserved. Relationships refer to physical archive row indexes; duplicate application UUIDs do not collapse distinct rows. Inverse relationships are rebuilt by SwiftData. There are no attachment entities or external-storage attributes in the current schema. Future schema additions must update the explicit archive registry and round-trip fixture. Restore validates the archive structure and physical relationship targets, not new-record business rules: duplicate logical IDs, unknown raw values and historical cross-project milestone links must remain recoverable. Import trusted Transit backups; hand-editing is unsupported. Cloud wipe separately refuses ambiguous duplicate-ID coverage.

Exports read a fresh saved context, excluding unsaved editor drafts. Scheduled exports and service-created recovery backups use a hidden pending file: it is read back, decoded, restored into a retained CloudKit-free in-memory container, and compared against the full original snapshot before a same-directory atomic rename publishes it. Verification failure removes the pending file and leaves any existing destination unchanged. Manual exports use the system document picker: the archive is test-restored before opening the picker, and the saved destination is read back and restored again before success or wipe confirmation. A failed picker save or read-back cannot authorize wiping; its destination may need to be removed or exported again. A share-sheet presentation or picker cancellation is not backup success. Service-created backups synchronize the file and parent directory before publication succeeds. System document-picker copies receive complete readback/restore verification; picker access does not authorize opening the parent folder. Their provider upload or remote durability cannot be guaranteed. Wipe additionally requires a newly durably published app-owned recovery copy, so no weaker flush or provider-readback alone authorizes deletion. Temporary files use exclusive creation and an advisory lock held through verification and publication. Each service export sweeps unlocked regular `.Transit-<UUID>.pending` files older than 24 hours from that destination only. Published backups, recent stages, active writers, symlinks and unknown files are preserved; this is crash-stage cleanup, not backup retention. Cleanup is best effort, including directory-listing failures; an individual undeletable orphan is preserved rather than preventing a new backup. Persistent snapshots compare saved-history watermarks before and after capture. The 128 MB safety limit is enforced before writing and while reading; larger archives are refused rather than partially imported. Decoding and scratch restoration need additional memory beyond the file size; near-limit files can encounter memory pressure, especially on iOS. Use a Mac for unusually large backups. An incomplete verification cannot authorize mutation.

Import is **replacement**, not merge or UUID upsert. It validates and test-restores the selected archive, writes and verifies a new recovery backup under the app's Application Support/Backups directory, checks that saved data and the shared context have not changed, then replaces all entities in one owned-context save. Failure before the save leaves the original dataset intact. The failed context is rolled back and discarded. Manual encoding, file reads, durable writes and scratch restoration run on the same background writer as scheduled exports; only immutable archives, bytes and URLs cross that boundary. The UI shows progress and keeps security-scoped file access open across awaits. After background work, availability, cancellation, the saved dataset and unsaved editor state are checked again immediately before the owned-context mutation, which has no suspension point. Wipe also binds the final read-back to the exact archive used for cloud preflight. Recovery backups are retained. Settings lists feature-owned recovery files and offers Save Recovery Copy, including after restart. After replacement, an interactive completion screen outside the editing lock provides restart guidance and those copy controls. Cancellation or copy failure preserves the original and allows another attempt. Import reports verification, recovery creation and record application stages; final capture/delete/insert/save remains synchronous and can briefly pause rendering for large datasets. With active iCloud sync, replacement propagates to other devices; it is not an account-wide transaction and another device can introduce later changes.

Receipts remain historical data. Mac exports also archive local retry reservations as recovery evidence, without reinstalling them as executable requests. Replacement refuses active or unresolved MCP writes, then stages a durable replacement journal before the database save and rotates the local retry namespace after commit. Startup resumes interrupted rotation. Old keys remain blocked through hashed tombstones; a crash between staging and the database save conservatively retires the keys even if the database stayed unchanged. The app pauses its listener, heartbeat and connectivity callbacks and requires a restart after successful replacement. Native controls and automation writes are blocked until restart, protecting cached editors and replay scopes. Cleanup failure after a committed replacement is explicitly reported as a committed operation requiring restart, not as a rolled-back import.

## Mac schedule

Choose a folder and enable daily exports; the initial example time is 02:00 in the Mac's current local time zone. Folder access uses a persisted security-scoped bookmark. No launch agent, privileged helper, device deployment or external scheduler is installed. While Transit is running it checks every minute. Saved capture stays on the UI actor; encoding, file I/O and the complete isolated restore run on a separate serial actor using only the immutable archive. No installed model or context crosses that boundary. Folder access remains open until publication finishes, and resolvable stale bookmarks are renewed. If the Mac sleeps or the app closes, one missed export runs when Transit next runs; there is no promise of an export while the app is closed. Enabling the schedule after today's chosen time starts with tomorrow's export. Daylight-saving gaps use the next valid local time and repeated hours use the first occurrence. Files are unique and retained until the user removes them. Failed exports do not advance the successful-export timestamp. Settings shows the last success and failure; failed exports retry at most hourly, and choosing the folder again clears the delay.

## Wipe and iCloud

The wipe flow first saves a new export to a user-selected destination and verifies the actual file with a complete isolated restore. The same exact archive is then saved, fully synchronized and verified in app-owned Application Support/Backups storage as a BeforeWipe recovery file. Only after both checks succeed does Transit offer typed `WIPE` confirmation. Final wipe rereads the durable private file; the selected copy is additional recovery access, without a guarantee of provider upload completion. The final saved dataset must still match the exact backup. Cancellation, an unreadable file, a failed restore, changed data or a failed save prevents deletion.

For an iCloud-capable app, sync must be active before wipe. An online preflight reads the app's private Core Data zone (CloudKit's always-present default zone is excluded because Transit never writes application data there) through paginated CloudKit changes and refuses unknown entities, cloud-only rows, differing stored fields or uncovered relationships. Duplicate physical application IDs refuse cloud wipe because cloud recovery coverage cannot be certified. The current Core Data CloudKit field mapping is checked conservatively; unexpected mapping fails closed. CloudKit mirror metadata, heartbeat traffic and display-ID counters are infrastructure rather than recoverable user content.

Deletion uses ordinary SwiftData entity deletions and its CloudKit export path. The UI states that iCloud deletion propagates as synchronization completes; this is not an immediate remote zone purge. CloudKit zones and schemas are never reset. Display-ID allocation infrastructure is retained to avoid reusing IDs on stale other devices. Quit Transit on other devices first: unseen concurrent/offline edits can later reintroduce data, and CloudKit offers no global all-device transaction. No live wipe, import, production launch or CloudKit mutation was exercised by automated verification; destructive checks use synthetic stores only.

## Mac scheduled-folder permission correction — 2026-10-10

User testing found `Operation not permitted` when creating the scheduled staging file. The app configurations granted selected files read-only access and omitted app-scoped bookmark capability. Mac signing now grants read/write access only to user-selected resources plus persistent app-scoped bookmarks, for local Development, opt-in Development cloud, and Release. Phone entitlement inputs remain separate. No Full Disk Access, global folder entitlement, or security-policy change is required. Existing read-only folder grants may require reselection.

Folder selection holds the system security scope while creating a bookmark and checking an exclusive disposable staging file on the background executor (write, full file flush, directory flush, removal). Only success replaces the previous folder/bookmark. Scheduler resolution retains the scope until its background verified publication finishes, renews stale bookmarks while scoped, and closes access on every completion/error path. Existing schedule/defaults values and catch-up/retry semantics remain unchanged. A native time-only field with stepper replaces the hour/minute menus, supports keyboard entry and the system locale’s 12/24-hour format. A neutral date anchor represents only wall-clock fields; schedule execution still uses the Mac’s local calendar including its existing DST policy.

Focused unit fixtures and configuration guards are distinct from native selection/relaunch acceptance; validation results are recorded in the implementation record.
